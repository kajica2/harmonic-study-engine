# ADR-024: Source-agnostic note-input seam - fallback surfaces feed the same pipeline as hardware

- Date: 2026-09-28
- Status: Accepted (PRD-001 Phase 7 Slice 4, D137..D144 + orchestrator ruling (b))
- Context: REQ-IO-4/5/6 - on-screen piano + computer-keyboard input when Web MIDI is unavailable - had to reach the S3 consumers (played-correctly detection, latency wizard, IN picker) without forking them, without touching the frozen synesthesia display piano, the sacred handler, or the zustand envelope.

## Decision

1. **ONE seam, tagged sources** (D137): fallback surfaces dispatch the SAME window `midin` CustomEvent the hardware midiIn already emits - detail shape field-by-field pinned against the midiIn.ts contract (channel 0, velocity 100/0, performance.now() timestamp), distinguished only by `inputId: "hse-keyboard" | "hse-screen"` sentinels matched EXACT (not prefix) by `isHseInputId()`. Channel 0 is load-bearing: it keeps every shipped bass-channel-exclusion consumer byte-identical. The typed `import type { MidiInEvent }` makes shape drift compile-impossible. Parallel input path REJECTED - forks three consumers + the e2e seam for zero gain; the midin seam is also the ONLY e2e-injectable one (S3 D135).
2. **Ruling (b): fallback notes never echo to midiOut** (orchestrator call on the design's open item): the App handleNoteInput path = audioEngine play/stop + recorder + setActiveMidis + bus dispatch, NO `midiOut.playNote`. Rationale: hardware MIDI INPUT notes never echo to output either (consistency), and a loopback rig would double-count a keyboard note into detection (synthetic event + hardware echo). External-gear driving stays the display piano's byte-untouched job. The design's risk row "MIDI-loopback double-count" is CLOSED by ruling, not by mitigation.
3. **Detection gate widened; PRD text superseded by PRD-internal resolution** (D138): arm gate = (Web MIDI API present) OR (note-input enabled); `hasDevice` stays HARDWARE-only (status-line honesty) with a new one-shot `sawFallback`; 4-state copy replaces the "requires Web MIDI" notice. REQ-PRAC-54's literal MIDI-only text conflicts with REQ-IO-4/5's P0 fallback mandate - resolved in favor of the fallback (both are the same PRD; the newer, P0 surface wins), erratum applied IN docs/PRD-001.md by the orchestrator, design doc §14 records it.
4. **Per-source latency, in-place widening, per-note correctness** (D141): LatencyRecord gains `fallbackInputLatencyMs` + `fallbackCalibratedAtMs`, `inputLatencyMs` widens to `number | null` (fallback-only calibration is legal); version stays 1, defaults-at-read, ZERO new K keys. The engine sees an optional `PerformedNote.compensationMs ?? global` override - hse buffer pushes stamp their source's compensation (0 is REAL - the `??` law, pinned), hardware pushes carry none. Mixed MIDI+keyboard passes are per-note correct with one shared sum site. Wizard save MERGES (loadLatency first) - neither source's calibration can clobber the other's; MIDI mode filters hse-* events (poison guard).
5. **Input-key doctrine: opt-in, default OFF, guard stack, never e.key** (D139): the AWSED+ZX mapping ships behind a persisted toggle (default off = zero regression), armed only on the study surface with no blocking modal; guard order typing -> modifier (strictly before any key branch, PHASE-1-01) -> e.repeat -> classify by `e.code` (the classifier's Pick<...,"code"|"metaKey"|"ctrlKey"|"altKey"> signature makes reading e.key UNREPRESENTABLE); preventDefault only on handled keys; release paths stay modifier-UNGATED (stuck-note law). Collision audit: all 15 keys free in shipped code.
6. **Parent-stance reversal discipline** (D144): a slice MAY pull scope the parent parked, when (a) the parent's premise is FALSE in shipped code (its "PianoKeyboard needs press handlers" claim - press handlers exist, they just never dispatch midin), (b) the PRD's own rollout line schedules it, and (c) the orchestrator ratifies. Mechanics: numbered decision, pointer erratum appended to the parent (never rewritten), ratification recorded here.
7. **First REAL-input positive e2e legs** (test plan 6.2): unlike MIDI, headless Chromium delivers TRUSTED keyboard/pointer events - leg 1 drives the app's own listener end-to-end (user key -> hook -> bus -> detector), the strongest input leg in the repo. Pigeonhole cadence law + monotonic counters; break-guard legs 1+2+4 FAIL on pre-S4 build.
